# Специфікація авторизації та реєстрації

> Петпроєкт Money Tracker. Документ описує перший повний вертикальний зріз керування обліковим записом: реєстрацію, вхід, перевірку поточної сесії, вихід і захист приватних маршрутів.

## 1. Ціль

Користувач повинен мати змогу створити обліковий запис за ім'ям, email і паролем, увійти до застосунку, залишатися авторизованим у межах браузерної сесії та безпечно вийти. Дані одного користувача не повинні бути доступні іншому.

Після успішної реєстрації або входу користувач переходить на `/dashboard`. Неавторизований користувач, який відкриває приватний маршрут, переходить на `/login`.

## 2. Межі задачі

### Реалізуємо

- реєстрацію за ім'ям, email і паролем;
- вхід за email і паролем;
- серверну сесію в PostgreSQL;
- отримання даних поточного користувача;
- вихід із поточної сесії;
- захист приватних API та web-маршрутів;
- спільні Zod-схеми й типи запитів/відповідей;
- rate limiting для входу та реєстрації;
- міграції БД, автоматизовані тести та структуровані логи.

### Не реалізуємо

- підтвердження email;
- відновлення або зміну пароля;
- OAuth та вхід через сторонні сервіси;
- двофакторну автентифікацію;
- ролі, команди або спільні простори;
- керування списком активних сесій;
- функцію «Запам'ятати мене»;
- видалення облікового запису.

Назва простору в поточному UI відображається як статичне значення `Особистий простір`. Окрема сутність простору не входить у цю задачу.

## 3. Основні сценарії

### 3.1. Реєстрація

1. Гість відкриває `/login?mode=register` або вибирає вкладку «Реєстрація».
2. Вводить ім'я, email і пароль.
3. Web виконує клієнтську перевірку та надсилає запит до API.
4. API повторно перевіряє дані, нормалізує email і перевіряє його унікальність.
5. API хешує пароль, створює користувача та сесію в одній транзакції.
6. API встановлює session cookie і повертає безпечне представлення користувача.
7. Web переходить на `/dashboard`.

Якщо email уже зареєстрований, форма залишається відкритою, введені ім'я та email зберігаються, а біля поля email з'являється повідомлення `Обліковий запис із таким email уже існує`.

### 3.2. Вхід

1. Гість відкриває `/login`.
2. Вводить email і пароль.
3. API нормалізує email, знаходить користувача та перевіряє хеш пароля.
4. Після успішної перевірки API створює нову сесію та встановлює cookie.
5. Web переходить на безпечний локальний URL із параметра `returnTo`, а за його відсутності — на `/dashboard`.

Для неіснуючого email і неправильного пароля API повертає однакову помилку `Неправильний email або пароль`, щоб не розкривати наявність облікового запису.

### 3.3. Перевірка сесії

- Під час відкриття приватної частини web отримує поточного користувача через `GET /api/v1/auth/me`.
- API читає session cookie, знаходить лише її хеш у БД і перевіряє строк дії.
- Відсутня, невідома або прострочена сесія має однаковий результат `401 Unauthorized`.
- Прострочена сесія видаляється під час перевірки або фоновим очищенням.

### 3.4. Вихід

1. Авторизований користувач натискає «Вийти».
2. Web надсилає `POST /api/v1/auth/logout`.
3. API видаляє поточну сесію з БД і очищає cookie.
4. Web очищає кеш даних користувача та переходить на `/login`.

Повторний вихід без активної сесії також повертає успішну відповідь.

## 4. Валідація та нормалізація

Однакові Zod-схеми з `@money-tracker/shared` використовуються web і API. Клієнтська валідація покращує UX, але не замінює серверну.

| Поле | Правила |
| --- | --- |
| `name` | Обов'язкове; обрізати пробіли на початку й у кінці; від 1 до 80 символів після обрізання |
| `email` | Обов'язкове; обрізати зовнішні пробіли; коректний формат; не більше 254 символів; для пошуку й унікальності привести до нижнього регістру |
| `password` | Обов'язкове; від 6 до 128 символів; не обрізати й не змінювати регістр |

Додаткові правила:

- пароль не записується в логи, аналітику, URL або стан, що зберігається в браузері;
- форма не змінює пароль мовчки: пробіли всередині та по краях є частиною пароля;
- API відхиляє невідомі поля в auth DTO;
- `email` зберігає введене значення після обрізання зовнішніх пробілів, а окремий `email_normalized` — його варіант у нижньому регістрі для пошуку й перевірки унікальності;
- мінімум у 6 символів залишено для узгодженості з функціональними вимогами MVP; посилення парольної політики оформлюється окремою зміною вимог.

## 5. UX web-застосунку

### 5.1. Маршрут `/login`

Екран наслідує `docs/visual-design/auth.html` і має дві вкладки:

- `Вхід`: email, пароль, кнопка `Увійти`;
- `Реєстрація`: ім'я, email, пароль, кнопка `Створити акаунт`.

Режим синхронізується з query-параметром `mode=login|register`. Невідоме значення відкриває режим входу. Перемикання вкладки не повинно переносити пароль між режимами.

Вимоги до форми:

- поля мають пов'язані `label`, `autocomplete` (`name`, `email`, `current-password`, `new-password`) та доступні тексти помилок;
- Enter відправляє активну валідну форму;
- під час запиту кнопка показує стан завантаження, а повторне відправлення блокується;
- помилки полів відображаються після blur або першої спроби відправлення;
- серверна помилка поля відображається біля поля, загальна — над формою;
- після помилки введені ім'я та email не втрачаються, пароль залишається тільки в локальному стані поточної форми;
- повідомлення про помилку має `role="alert"`, фокус переходить на перше невалідне поле;
- елементи керування мають видимий keyboard focus;
- посилання `До огляду` з макета прибирається: приватний огляд не можна відкривати без сесії.

### 5.2. Навігація й перенаправлення

- `/dashboard`, `/expenses`, `/categories`, `/profile` є приватними маршрутами.
- Гість переходить на `/login?returnTo=<локальний-шлях>`.
- `returnTo` приймає лише шлях поточного origin, що починається з `/`; абсолютні URL, `//host` і значення з іншого origin ігноруються.
- Авторизований користувач при відкритті `/login` переходить на `/dashboard`.
- Коротке завантаження перевірки сесії не повинно показувати приватний контент або миготіння форми входу.
- Отриманий через `GET /auth/me` користувач є джерелом істини для імені та ініціалів у shell застосунку.

## 6. API

Базовий префікс: `/api/v1/auth`. Web звертається до API через same-origin `/api`, який у локальній розробці проксіюється Next.js до NestJS. Це усуває необхідність у permissive CORS для основного web-клієнта.

### 6.1. `POST /api/v1/auth/register`

Запит:

```json
{
  "name": "Володимир",
  "email": "volodymyr@example.com",
  "password": "secret123"
}
```

Успіх: `201 Created`, встановлена session cookie.

```json
{
  "user": {
    "id": "8e8ec0df-8e02-4d12-a708-b8f4ea0f158e",
    "name": "Володимир",
    "email": "volodymyr@example.com"
  }
}
```

Помилки: `400 VALIDATION_ERROR`, `409 EMAIL_ALREADY_EXISTS`, `429 RATE_LIMITED`.

### 6.2. `POST /api/v1/auth/login`

Запит:

```json
{
  "email": "volodymyr@example.com",
  "password": "secret123"
}
```

Успіх: `200 OK`, встановлена нова session cookie та така сама `user`-відповідь, як при реєстрації.

Помилки: `400 VALIDATION_ERROR`, `401 INVALID_CREDENTIALS`, `429 RATE_LIMITED`.

### 6.3. `GET /api/v1/auth/me`

Успіх: `200 OK`.

```json
{
  "user": {
    "id": "8e8ec0df-8e02-4d12-a708-b8f4ea0f158e",
    "name": "Володимир",
    "email": "volodymyr@example.com"
  }
}
```

Помилка без чинної сесії: `401 UNAUTHENTICATED`.

### 6.4. `POST /api/v1/auth/logout`

Тіло запиту відсутнє. Успіх: `204 No Content`; cookie очищена через `Max-Age=0`. Endpoint ідемпотентний.

### 6.5. Формат помилки

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Перевірте введені дані",
    "fields": {
      "email": ["Вкажіть коректний email"]
    },
    "traceId": "01JZ8N5QW7Q7B2XJ9FXXG84V4R"
  }
}
```

- `code` — стабільний машинний код;
- `message` — безпечний текст для користувача українською;
- `fields` присутній лише для помилок конкретних полів;
- `traceId` відповідає `trace_id` у структурованих логах;
- stack trace, SQL-помилки та внутрішні деталі не повертаються клієнту.

Усі auth-відповіді містять `Cache-Control: no-store`.

## 7. Сесія та cookie

Використовується opaque session token, а не JWT. Це спрощує негайне відкликання сесії під час виходу й не переносить дані користувача в браузер.

- токен генерується криптографічно стійким генератором і має щонайменше 256 біт ентропії;
- у cookie передається сирий токен, у БД зберігається тільки його SHA-256 хеш;
- строк дії сесії — 24 години від створення без автоматичного продовження;
- cookie є непостійною: без `Expires` і `Max-Age`, тому закриття браузерної сесії завершує клієнтську сесію;
- кожна успішна реєстрація або авторизація створює новий токен;
- токен не приймається через query, JSON body або `Authorization` header.

Production cookie:

```http
Set-Cookie: __Host-mt_session=<token>; Path=/; HttpOnly; Secure; SameSite=Lax
```

Атрибут `Domain` не встановлюється. Для локального HTTP використовується окреме ім'я `mt_session` і `Secure=false`; усі інші атрибути незмінні. Production-конфігурація без HTTPS або без `Secure=true` повинна завершувати запуск API з помилкою.

`HttpOnly`, `Secure`, вузький host scope і `SameSite` відповідають рекомендаціям OWASP та MDN щодо захисту session cookie. Токени не зберігаються в `localStorage` або `sessionStorage`.

## 8. Модель даних

Для PostgreSQL додаються міграції та дві таблиці.

### `users`

| Колонка | Тип | Обмеження |
| --- | --- | --- |
| `id` | `uuid` | primary key, генерується сервером |
| `name` | `varchar(80)` | not null |
| `email` | `varchar(254)` | not null |
| `email_normalized` | `varchar(254)` | not null, unique |
| `password_hash` | `text` | not null |
| `created_at` | `timestamptz` | not null, default now |
| `updated_at` | `timestamptz` | not null, оновлюється при зміні |

### `sessions`

| Колонка | Тип | Обмеження |
| --- | --- | --- |
| `id` | `uuid` | primary key |
| `user_id` | `uuid` | not null, foreign key `users.id`, on delete cascade |
| `token_hash` | `char(64)` | not null, unique |
| `expires_at` | `timestamptz` | not null, indexed |
| `created_at` | `timestamptz` | not null, default now |

Відповіді API та логи ніколи не містять `password_hash` або `token_hash`.

Конкретний ORM може бути обраний під час реалізації, але міграції є єдиним способом змінювати production-схему. Автоматична синхронізація схеми під час старту заборонена.

## 9. Серверна архітектура

`apps/api/src/auth` містить:

- controller для чотирьох endpoint-ів;
- service для сценаріїв реєстрації, входу, перевірки та виходу;
- session guard для приватних endpoint-ів;
- password hasher adapter;
- session repository та user repository;
- rate-limit policy;
- mapper безпечного `AuthUser`.

`packages/shared` експортує:

- `registerRequestSchema` / `RegisterRequest`;
- `loginRequestSchema` / `LoginRequest`;
- `authUserSchema` / `AuthUser`;
- `authResponseSchema` / `AuthResponse`;
- `apiErrorSchema` / `ApiError`;
- enum або union стабільних auth error codes.

Контролери не працюють із БД напряму. Guard додає до request лише безпечного поточного користувача або його `userId`.

## 10. Безпека

### Паролі

- пароль хешується Argon2id з унікальною випадковою salt;
- мінімальна конфігурація: `m=19456 KiB`, `t=2`, `p=1`; перед production параметри перевіряються навантажувальним тестом;
- під час входу використовується verify-функція бібліотеки, а не ручне порівняння;
- plaintext-пароль існує тільки в пам'яті на час обробки запиту;
- для невідомого email виконується перевірка проти службового Argon2id-хешу, щоб зменшити різницю в часі відповіді;
- секретний pepper не є обов'язковим для MVP.

Параметри Argon2id відповідають актуальній мінімальній конфігурації [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

### CSRF і запити

- для `POST` endpoint-ів API перевіряє `Origin` за allowlist; відсутній або чужий origin у браузерному запиті відхиляється;
- API приймає auth body тільки з `Content-Type: application/json`;
- `SameSite=Lax` є додатковим, а не єдиним CSRF-захистом;
- production CORS вимкнений для same-origin deployment; якщо його буде ввімкнено, дозволяється лише точний web origin із credentials, без `*`;
- state-changing дії не реалізуються через `GET`.

### Rate limiting

- login: не більше 5 невдалих спроб за 15 хвилин для комбінації IP + normalized email;
- register: не більше 3 спроб за годину для IP і 3 спроб за годину для normalized email;
- успішний вхід скидає лічильник невдалих спроб для відповідної комбінації;
- відповідь `429` містить `Retry-After`;
- rate-limit сховище має працювати для кількох інстансів API; локально дозволене in-memory сховище, production — спільне зовнішнє сховище;
- IP із proxy headers довіряється лише за правильно налаштованого списку trusted proxies.

Rate limiting не повинен блокувати обліковий запис глобально: інакше стороння особа могла б спричинити denial of service для відомого email.

## 11. Логи й спостережуваність

Події пишуться структуровано у JSON і містять `trace_id`, `event`, `outcome`, `duration_ms` та, коли доступно, `user_id`.

Події:

- `auth.register.succeeded` / `auth.register.failed`;
- `auth.login.succeeded` / `auth.login.failed`;
- `auth.session.rejected`;
- `auth.logout.succeeded`;
- `auth.rate_limited`.

Заборонено логувати пароль, session token, cookie header, password/session hash і повний email. Для діагностики email можна замінити незворотним HMAC-ідентифікатором. Очікувані `401` не логуються як server error; неочікувані помилки мають рівень `error` і stack trace лише в серверному лозі.

## 12. Обробка конкурентності та помилок

- унікальний індекс `email_normalized` є остаточним захистом від паралельної реєстрації;
- конфлікт унікальності перетворюється на `409 EMAIL_ALREADY_EXISTS`, а не `500`;
- користувач і перша сесія під час реєстрації створюються атомарно;
- якщо встановлення відповіді перервано, створена серверна сесія може бути видалена фоновим очищенням після завершення TTL;
- помилка БД або хешування повертає безпечний `500 INTERNAL_ERROR` із `traceId`;
- усі дати обчислюються на сервері в UTC і зберігаються як `timestamptz`.

## 13. Тести

### Unit

- усі shared Zod-схеми: валідні значення та кожна межа;
- нормалізація email імені без зміни пароля;
- створення й хешування session token;
- перевірка чинної, невідомої та простроченої сесії;
- мапінг DB constraint у стабільний API error;
- валідація безпечного `returnTo`.

### API integration

- реєстрація створює користувача, хеш пароля та сесію;
- однаковий email у різному регістрі повертає `409`;
- plaintext-пароль і сирий session token відсутні в БД та відповіді;
- правильний пароль виконує вхід, неправильний повертає `401`;
- `me` працює лише з чинною cookie;
- logout видаляє тільки поточну сесію та очищає cookie;
- expired session повертає `401`;
- cookie має потрібні production-атрибути;
- чужий `Origin`, неправильний content type і перевищення rate limit відхиляються;
- помилки містять `traceId`, а логи — той самий `trace_id`.

Інтеграційні тести працюють з окремою PostgreSQL-базою та застосовують реальні міграції.

### Web component/E2E

- перемикання вкладок і query-параметра;
- клієнтські помилки та keyboard submit;
- loading/disabled стан без подвійного submit;
- успішні реєстрація, вхід і вихід;
- показ серверної помилки без втрати імені та email;
- перенаправлення гостя з приватного маршруту й повернення через `returnTo`;
- відхилення зовнішнього `returnTo`;
- відсутність короткого показу приватного контенту гостю.

## 14. Змінні середовища

Приклади додаються до `.env.example` без реальних секретів:

```dotenv
AUTH_SESSION_TTL_SECONDS=86400
AUTH_COOKIE_NAME=mt_session
AUTH_COOKIE_SECURE=false
AUTH_ALLOWED_ORIGINS=http://localhost:3000
AUTH_TRUST_PROXY=false
DATABASE_URL=postgresql://money_tracker:money_tracker@localhost:5432/money_tracker
```

Для production ім'я cookie — `__Host-mt_session`, `AUTH_COOKIE_SECURE=true`, а дозволені origin-и містять лише HTTPS URL розгорнутого web-застосунку.

## 15. Acceptance Criteria

- [ ] На `/login` працюють режими входу та реєстрації згідно з макетом і правилами доступності.
- [ ] Користувач може зареєструватися за валідними ім'ям, email і паролем та одразу потрапляє на `/dashboard`.
- [ ] Email є унікальним без урахування регістру; паралельна повторна реєстрація не створює дубль.
- [ ] Пароль зберігається лише як Argon2id-хеш; API та логи не повертають секретні значення.
- [ ] Користувач може увійти з правильними даними; помилка для невідомого email і неправильного пароля однакова.
- [ ] Session token має достатню ентропію, у БД зберігається лише його SHA-256 хеш.
- [ ] Cookie має `HttpOnly`, `SameSite=Lax`, `Path=/`, production `Secure` і не має `Domain`.
- [ ] `GET /api/v1/auth/me` повертає поточного користувача лише для чинної сесії.
- [ ] Вихід відкликає поточну сесію, очищає cookie та є ідемпотентним.
- [ ] Приватні web-маршрути й API недоступні без сесії; `returnTo` не створює open redirect.
- [ ] Auth endpoint-и мають перевірку Origin, JSON content type та задані rate limits.
- [ ] DTO і відповіді описані спільними Zod-схемами в `@money-tracker/shared`.
- [ ] Міграції створюють таблиці та індекси з розділу «Модель даних».
- [ ] Unit, API integration і web/E2E тести з розділу «Тести» проходять.
- [ ] `npm run build`, `npm run lint`, `npm run typecheck`, `npm run test` і `npm run format:check` проходять із кореня.
