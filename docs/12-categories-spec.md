# Специфікація категорій бюджету

> Петпроєкт Money Tracker. Документ описує повний вертикальний зріз керування категоріями: список, створення, редагування, видалення, місячні бюджетні розрахунки та інтеграцію з витратами.

## 1. Ціль

Авторизований користувач повинен мати змогу створювати власні категорії витрат, задавати для них місячний бюджет, редагувати й видаляти їх та бачити використання бюджету за поточний календарний місяць.

Категорії одного користувача не доступні іншому. Зміни категорій мають одразу впливати на екран `/categories`, огляд бюджету та вибір категорії у формі витрати.

## 2. Межі задачі

### Реалізуємо

- приватний маршрут `/categories` згідно з `docs/visual-design/categories.html`;
- отримання активних категорій поточного користувача;
- створення й редагування категорії;
- логічне видалення категорії без втрати пов'язаних витрат;
- місячний бюджет у гривні з точністю до копійки;
- розрахунок витраченої суми, залишку та відсотка використання;
- загальний бюджет і загальну використану суму активних категорій;
- спільні Zod-схеми та TypeScript-типи для web і API;
- міграцію PostgreSQL, автоматизовані тести та структуровані логи;
- узгодження категорій із формою створення й редагування витрати.

### Не реалізуємо

- вкладені категорії та довільну ієрархію;
- окремі бюджети для різних місяців або історію зміни бюджету;
- перенесення невикористаного залишку на наступний місяць;
- спільні, системні або командні категорії;
- дохідні категорії;
- іконки та кольори, які налаштовує користувач;
- сортування категорій drag-and-drop;
- відновлення видалених категорій у UI;
- жорстку заборону створювати витрати понад бюджет;
- імпорт, експорт і масові операції.

## 3. Терміни та бізнес-правила

### 3.1. Активна категорія

Категорія є активною, поки `archived_at` дорівнює `null`. Тільки активні категорії:

- відображаються на `/categories`;
- доступні для нових витрат;
- входять до загального бюджету;
- враховуються у підсумку «Використано» на екрані категорій.

Дія «Видалити» у користувацькому інтерфейсі архівує категорію. Фізичне видалення не використовується, тому раніше створені витрати зберігають посилання на категорію та її назву.

### 3.2. Місячний бюджет

`monthlyBudgetMinor` — поточний повторюваний бюджет категорії на один календарний місяць. Значення не є лімітом: користувач може створювати витрати після перевищення бюджету, а UI показує перевитрату.

У межах MVP зберігається тільки актуальне значення бюджету. Редагування бюджету:

- одразу змінює розрахунки поточного місяця;
- не змінює суми витрат;
- не створює історичну версію бюджету.

Перш ніж додавати перегляд минулих бюджетних періодів, необхідно окремо спроєктувати таблицю версій бюджету. Поточне значення не можна подавати користувачу як історичний бюджет.

### 3.3. Поточний місяць

Поточний бюджетний період визначає API в часовій зоні `APP_TIME_ZONE`; для MVP значення за замовчуванням — `Europe/Kyiv`. Межі періоду повертаються як календарні дати у форматі `YYYY-MM-DD`.

Позначка часу створення або редагування сутності зберігається в UTC як `timestamptz`. Дата витрати є календарною датою, а не UTC timestamp. Для серпня 2026 року діапазон витрат має вигляд `2026-08-01 <= expense_date < 2026-09-01`.

### 3.4. Грошові значення

- API та БД передають і зберігають гроші цілим числом копійок;
- `100` означає `1,00 грн`, а `1250000` — `12 500,00 грн`;
- обчислення через JavaScript `number` із гривнями з плаваючою крапкою заборонене;
- у UI значення форматується через `Intl.NumberFormat("uk-UA", { style: "currency", currency: "UAH" })`;
- форма приймає гривні з не більш ніж двома десятковими знаками та перетворює їх у копійки до відправлення API.

## 4. Основні сценарії

### 4.1. Перегляд категорій

1. Користувач відкриває `/categories`.
2. Web перевіряє сесію і запитує список категорій.
3. API визначає поточний місяць, отримує активні категорії користувача та одним агрегованим запитом рахує витрати.
4. Web показує категорії, прогрес кожної категорії та загальні показники.

Категорії сортуються від найновішої до найстарішої за `created_at DESC, id DESC`. Новостворена категорія з'являється на початку списку.

### 4.2. Створення

1. Користувач натискає `Категорія`.
2. Відкривається діалог `Нова категорія` з полями `Назва`, `Тип`, `Місячний бюджет`.
3. Web перевіряє поля та надсилає запит.
4. API повторно перевіряє дані, нормалізує назву та створює категорію.
5. Діалог закривається, список і загальні показники оновлюються, з'являється повідомлення `Категорію створено`.

Якщо активна категорія з такою назвою вже існує, діалог залишається відкритим, введені дані не втрачаються, а біля назви з'являється `Активна категорія з такою назвою вже існує`.

### 4.3. Редагування

1. Користувач натискає кнопку редагування в рядку категорії.
2. Діалог `Редагувати категорію` відкривається з поточними значеннями.
3. Після збереження API атомарно оновлює категорію та збільшує її `version`.
4. Web повторно отримує список і залежні бюджетні дані.

Перейменування категорії змінює назву для всіх пов'язаних витрат, оскільки витрата посилається на категорію за `category_id`, а не зберігає копію назви. Зміна типу не впливає на розрахунки.

Якщо категорію змінили в іншій вкладці після відкриття діалогу, API не перезаписує новіші дані та повертає конфлікт версії. Web залишає форму відкритою і пропонує оновити дані.

### 4.4. Видалення

1. Користувач натискає кнопку видалення.
2. Web відкриває підтвердження: `Видалити категорію «{назва}»? Вона зникне зі списку та нових витрат. Існуючі витрати збережуться.`
3. Після підтвердження API встановлює `archived_at`, збільшує `version` і повертає `204 No Content`.
4. Web прибирає категорію зі списку, перераховує підсумки й показує `Категорію видалено`.

Архівування має такі наслідки:

- бюджет категорії більше не входить до загального бюджету;
- витрати категорії більше не входять до підсумку «Використано» саме на екрані активних категорій;
- загальна сума всіх витрат на `/dashboard` не змінюється;
- існуючі витрати продовжують показувати категорію;
- нову активну категорію з такою самою назвою можна створити, але вона матиме новий `id` і не отримає старі витрати.

Скасування підтвердження не надсилає запит і не змінює дані.

## 5. Валідація та нормалізація

Однакові Zod-схеми з `@money-tracker/shared` використовуються web і API. API відхиляє невідомі поля.

| Поле | Правила |
| --- | --- |
| `name` | Обов'язкове; Unicode NFC; обрізати зовнішні пробіли; послідовності внутрішніх пробільних символів замінити одним пробілом; від 1 до 80 символів |
| `type` | Обов'язкове; така сама нормалізація пробілів; від 1 до 50 символів |
| `monthlyBudgetMinor` | Обов'язкове ціле число; від `1` до `99999999999` копійок включно |

`type` у MVP є коротким довільним текстом, наприклад `Щоденні`, `Обов'язкові`, `Побут` або `Планові`. Це не enum і він не впливає на бізнес-логіку.

Для перевірки унікальності API формує `name_normalized` із нормалізованої назви у нижньому регістрі. Назви мають бути унікальними без урахування регістру лише серед активних категорій одного користувача. Остаточним захистом є частковий унікальний індекс БД.

Форма бюджету:

- приймає `2500`, `2500,5`, `2500.50`;
- не приймає нуль, від'ємне значення, експоненційний запис, більше двох десяткових знаків або значення вище максимуму;
- не очищає введені дані після серверної помилки;
- показує помилку біля відповідного поля.

## 6. Бюджетні розрахунки

Для кожної активної категорії API рахує:

```text
spentMinor = сума amount_minor активних витрат категорії за поточний місяць
remainingMinor = monthlyBudgetMinor - spentMinor
usagePercent = round(spentMinor / monthlyBudgetMinor * 100)
```

Правила:

- категорія без витрат має `spentMinor = 0`, `remainingMinor = monthlyBudgetMinor`, `usagePercent = 0`;
- `remainingMinor` може бути від'ємним;
- `usagePercent` може перевищувати `100` і в API не обрізається;
- заповнення progress bar візуально обмежується `100%`, але поруч відображається реальний відсоток;
- видалені витрати не враховуються, якщо модель витрат підтримує логічне видалення;
- усі суми виконуються в PostgreSQL над цілими значеннями, а не накопичуються у браузері.

Загальні показники:

```text
totalBudgetMinor = сума monthlyBudgetMinor усіх активних категорій
totalSpentMinor = сума spentMinor усіх активних категорій
```

За відсутності категорій обидві суми дорівнюють нулю. `totalSpentMinor` на `/categories` може відрізнятися від загальної суми витрат на `/dashboard`, якщо існують витрати архівованих категорій.

## 7. UX web-застосунку

### 7.1. Маршрут `/categories`

Екран наслідує `docs/visual-design/categories.html`, `expense-app.css` та `expense-app.js`:

- заголовок `Бюджети за призначенням`;
- основна кнопка `Категорія`;
- панель зі списком і лічильником `{N} активні`;
- для рядка: назва, тип, витрачена сума, прогрес бюджету, бюджет і дії;
- панель підсумків `Загальний бюджет` та `Використано`;
- діалоги створення, редагування й підтвердження видалення.

Граматична форма лічильника має бути коректною: `1 активна`, `2 активні`, `5 активних`.

Стани бюджету використовують семантичні кольори:

- менше `80%` — primary;
- від `80%` до `99%` — warning;
- `100%` і більше — error.

Колір не є єдиним способом передати стан: числовий відсоток і суми залишаються видимими.

### 7.2. Стани сторінки

- під час першого завантаження показуються skeleton-и структури, без фальшивих сум;
- при помилці завантаження показується безпечне повідомлення та кнопка `Спробувати ще`;
- якщо категорій немає, показується порожній стан `Категорій ще немає` з дією `Створити категорію`;
- під час mutation відповідна кнопка показує loading-стан, повторна відправка блокується;
- після успішної дії залежні дані оновлюються із сервера, а не залишаються лише в локальному стані;
- якщо оновлення списку після успішної mutation не вдалося, успішна дія не подається як помилка збереження: UI повідомляє, що дані збережено, і пропонує повторити завантаження.

### 7.3. Доступність і адаптивність

- діалог має заголовок, опис і коректне керування фокусом;
- після відкриття фокус переходить у поле назви, після закриття — на кнопку, що відкрила діалог;
- Escape і кнопка `Скасувати` закривають форму, якщо запит ще не відправляється;
- помилки мають бути пов'язані з полями та оголошуватися assistive technology;
- кнопки редагування й видалення мають доступні назви `Редагувати {назва}` та `Видалити {назва}`;
- progress bar має доступну назву з фактичним відсотком; значення `aria-valuenow` обмежується 100, а перевитрата пояснюється текстом;
- усі дії доступні з клавіатури й мають видимий focus state;
- на вузькому екрані підсумки переходять під список, рядки не створюють горизонтального прокручування, основні дії лишаються доступними;
- реалізація перевіряється щонайменше на viewport-ах із `DESIGN-HANDOFF.md`.

## 8. API

Базовий префікс: `/api/v1/categories`. Усі endpoint-и вимагають чинну сесію. Відповіді з фінансовими даними містять `Cache-Control: private, no-store`.

### 8.1. `GET /api/v1/categories`

Повертає активні категорії та розрахунки за поточний місяць.

Успіх: `200 OK`.

```json
{
  "period": {
    "month": "2026-08",
    "startsOn": "2026-08-01",
    "endsBefore": "2026-09-01",
    "timeZone": "Europe/Kyiv"
  },
  "categories": [
    {
      "id": "44638959-f635-4d85-a273-9351c60c7829",
      "name": "Їжа",
      "type": "Обов'язкові",
      "monthlyBudgetMinor": 1250000,
      "spentMinor": 824000,
      "remainingMinor": 426000,
      "usagePercent": 66,
      "version": 1,
      "createdAt": "2026-08-01T08:30:00.000Z",
      "updatedAt": "2026-08-01T08:30:00.000Z"
    }
  ],
  "summary": {
    "activeCount": 1,
    "totalBudgetMinor": 1250000,
    "totalSpentMinor": 824000
  }
}
```

Список не потребує пагінації в MVP. Агрегація витрат виконується одним запитом або еквівалентною сталою кількістю запитів, без N+1.

### 8.2. `POST /api/v1/categories`

Запит:

```json
{
  "name": "Їжа",
  "type": "Обов'язкові",
  "monthlyBudgetMinor": 1250000
}
```

Успіх: `201 Created`.

```json
{
  "category": {
    "id": "44638959-f635-4d85-a273-9351c60c7829",
    "name": "Їжа",
    "type": "Обов'язкові",
    "monthlyBudgetMinor": 1250000,
    "version": 1,
    "createdAt": "2026-08-01T08:30:00.000Z",
    "updatedAt": "2026-08-01T08:30:00.000Z"
  }
}
```

Помилки: `400 VALIDATION_ERROR`, `401 UNAUTHENTICATED`, `409 CATEGORY_NAME_ALREADY_EXISTS`.

### 8.3. `PATCH /api/v1/categories/:categoryId`

Оновлює передані поля. Має бути передане хоча б одне поле. Заголовок `If-Match` обов'язковий і містить поточну версію у форматі `"1"`.

```http
If-Match: "1"
Content-Type: application/json
```

```json
{
  "name": "Продукти та кафе",
  "monthlyBudgetMinor": 1350000
}
```

Успіх: `200 OK`, відповідь має ту саму форму `category`, що й створення, з `version: 2`.

Помилки: `400 VALIDATION_ERROR`, `401 UNAUTHENTICATED`, `404 CATEGORY_NOT_FOUND`, `409 CATEGORY_NAME_ALREADY_EXISTS`, `409 CATEGORY_VERSION_CONFLICT`, `428 VERSION_REQUIRED`.

### 8.4. `DELETE /api/v1/categories/:categoryId`

Логічно видаляє категорію. Заголовок `If-Match` обов'язковий і має такий самий формат, як для редагування.

Успіх: `204 No Content`. Повторний DELETE категорії, яку вже архівував той самий користувач, також повертає `204`, незалежно від старої версії. Для чужого або невідомого `id` повертається `404 CATEGORY_NOT_FOUND`.

Помилки: `401 UNAUTHENTICATED`, `404 CATEGORY_NOT_FOUND`, `409 CATEGORY_VERSION_CONFLICT`, `428 VERSION_REQUIRED`.

### 8.5. Формат помилки

Використовується спільний формат із auth-специфікації:

```json
{
  "error": {
    "code": "CATEGORY_NAME_ALREADY_EXISTS",
    "message": "Активна категорія з такою назвою вже існує",
    "fields": {
      "name": ["Виберіть іншу назву"]
    },
    "traceId": "01JZ8N5QW7Q7B2XJ9FXXG84V4R"
  }
}
```

Внутрішні SQL-помилки, stack trace та дані іншого користувача не повертаються клієнту.

## 9. Модель даних

Міграція додає таблицю `categories`.

| Колонка | Тип | Обмеження |
| --- | --- | --- |
| `id` | `uuid` | primary key, генерується сервером |
| `user_id` | `uuid` | not null, foreign key `users.id`, on delete cascade |
| `name` | `varchar(80)` | not null |
| `name_normalized` | `varchar(80)` | not null |
| `type` | `varchar(50)` | not null |
| `monthly_budget_minor` | `bigint` | not null, check від `1` до `99999999999` |
| `version` | `integer` | not null, default `1`, check `version > 0` |
| `archived_at` | `timestamptz` | nullable |
| `created_at` | `timestamptz` | not null, default now |
| `updated_at` | `timestamptz` | not null, оновлюється при зміні |

Обов'язкові індекси:

- частковий unique index на `(user_id, name_normalized) WHERE archived_at IS NULL`;
- index на `(user_id, created_at DESC) WHERE archived_at IS NULL`;
- index витрат на `(user_id, category_id, expense_date)` для місячної агрегації.

Таблиця витрат повинна зберігати `category_id uuid NOT NULL` із foreign key на `categories.id` та `ON DELETE RESTRICT`. Фізичне видалення категорії прикладним кодом заборонене.

PostgreSQL `bigint` драйвер може повертати як рядок. Repository зобов'язаний безпечно перетворити грошове значення на JavaScript `number` лише після перевірки `Number.isSafeInteger`; встановлена верхня межа вкладається в safe integer range.

## 10. Серверна архітектура

`apps/api/src/categories` містить:

- controller для list/create/update/delete;
- service з бізнес-правилами та перевіркою власника;
- category repository;
- агрегатор витрат поточного місяця;
- mapper API-відповідей;
- clock/time-zone adapter для детермінованого визначення місяця в тестах.

`packages/shared` експортує:

- `createCategoryRequestSchema` / `CreateCategoryRequest`;
- `updateCategoryRequestSchema` / `UpdateCategoryRequest`;
- `categorySchema` / `Category`;
- `categoryWithBudgetUsageSchema` / `CategoryWithBudgetUsage`;
- `categoryListResponseSchema` / `CategoryListResponse`;
- стабільні category error codes.

Контролер не звертається до БД напряму. `userId` береться тільки з перевіреної серверної сесії та ніколи — з body, query або довільного заголовка клієнта.

## 11. Інтеграція з витратами та оглядом

- форма нової витрати отримує лише активні категорії поточного користувача;
- запит створення витрати передає `categoryId`, а не назву категорії;
- API витрат перевіряє, що категорія належить користувачу й активна;
- редагування витрати, яка вже посилається на архівовану категорію, може залишити цю категорію без змін, але замінити її можна лише на активну;
- створення витрати й архівування категорії синхронізуються блокуванням відповідного рядка категорії в транзакції, щоб нова витрата не була прив'язана після завершення архівування;
- після category mutation web інвалідує або повторно отримує category list, dashboard summary і options у формі витрати;
- після expense mutation оновлюються `spentMinor`, `remainingMinor`, `usagePercent` і summary категорій.

## 12. Безпека

- усі category endpoint-и захищені session guard із `docs/11-authentication-registration-spec.md`;
- кожен repository-запит фільтрує дані за `user_id`;
- доступ до чужого UUID повертає `404`, а не `403`, щоб не підтверджувати існування ресурсу;
- `POST`, `PATCH` і `DELETE` перевіряють `Origin` за тим самим allowlist, що й auth mutation;
- body приймається лише як `application/json` для `POST` і `PATCH`;
- назва та тип відображаються React як текст; вставка через raw HTML заборонена;
- endpoint-и не приймають довільні SQL sort/filter expressions;
- відповіді не кешуються у shared/public cache.

## 13. Конкурентність і помилки

- `version` реалізує optimistic locking для редагування й видалення;
- update виконується атомарно з умовою `id`, `user_id`, `archived_at IS NULL` і поточної `version`;
- частковий unique index є остаточним захистом від паралельного створення або перейменування в однакову назву;
- DB unique violation перетворюється на `409 CATEGORY_NAME_ALREADY_EXISTS`;
- неочікувана помилка БД повертає `500 INTERNAL_ERROR` із `traceId` і не змінює локальний список як начебто успішний;
- усі записи category mutation виконуються транзакційно;
- API не покладається на обчислені клієнтом `spentMinor`, `remainingMinor` або `usagePercent` і відхиляє ці поля у mutation body.

## 14. Логи та спостережуваність

Структуровані JSON-події містять `trace_id`, `event`, `outcome`, `duration_ms`, `user_id` і, після створення або пошуку сутності, `category_id`.

Події:

- `category.list.succeeded` / `category.list.failed`;
- `category.create.succeeded` / `category.create.failed`;
- `category.update.succeeded` / `category.update.failed`;
- `category.archive.succeeded` / `category.archive.failed`;
- `category.version_conflict`.

Назва та тип категорії не записуються в логи. Очікувані `400`, `404` і `409` не логуються як server error. Неочікувані помилки мають рівень `error`, а stack trace залишається лише в серверному лозі.

## 15. Тести

### Unit

- нормалізація назви й типу, межі довжини та невідомі поля;
- перетворення гривень із UI у копійки без похибки floating point;
- мінімум, максимум і перевірка safe integer;
- визначення поточного місяця на межі місяця в `Europe/Kyiv`;
- розрахунок нульового, частково використаного, повністю використаного й перевищеного бюджету;
- граматична форма лічильника активних категорій;
- мапінг DB constraint і version conflict у стабільні API-помилки.

### API integration

- endpoint-и повертають `401` без сесії;
- користувач бачить лише власні категорії;
- create зберігає нормалізовані дані й суму в копійках;
- однакові активні назви в різному регістрі повертають `409`;
- різні користувачі можуть мати однакові назви;
- list правильно агрегує витрати лише за поточний місяць;
- витрати на межах `startsOn` та `endsBefore` включаються або виключаються правильно;
- list не виконує N+1 запити;
- update змінює тільки передані поля та збільшує `version`;
- застаріла версія update/delete повертає `409`;
- archive прибирає категорію зі списку, але не видаляє витрати;
- повторний archive повертає `204`;
- після archive таку саму назву можна використати для нової категорії з новим `id`;
- чужий `categoryId` повертає `404` для update і delete;
- чужий Origin і неправильний content type відхиляються;
- mutation не приймає `spentMinor`, `userId`, `archivedAt` та інші невідомі поля.

Інтеграційні тести працюють з окремою PostgreSQL-базою та застосовують реальні міграції.

### Web component/E2E

- loading, error і empty state;
- відкриття, скасування й keyboard submit форми;
- клієнтські помилки для кожного поля;
- create/update без подвійного submit і без втрати даних після API-помилки;
- duplicate-name та version-conflict UX;
- підтвердження і скасування видалення;
- оновлення рядків, загальних показників і dashboard після mutation;
- progress bar і семантичний стан для `<80%`, `80–99%` та `>=100%`;
- правильні accessible names і повернення фокуса;
- відсутність горизонтального прокручування на підтримуваних viewport-ах.

## 16. Змінні середовища

До `.env.example` додається:

```dotenv
APP_TIME_ZONE=Europe/Kyiv
```

API перевіряє IANA time zone під час запуску й завершує старт із зрозумілою помилкою, якщо значення некоректне.

## 17. Acceptance Criteria

- [ ] `/categories` є приватним маршрутом і візуально відповідає наданому дизайну на підтримуваних viewport-ах.
- [ ] Користувач бачить лише власні активні категорії, відсортовані від найновішої.
- [ ] Категорію можна створити, відредагувати й видалити через доступні діалоги з усіма UX-станами.
- [ ] Назва й тип проходять визначену нормалізацію, бюджет зберігається цілим числом копійок.
- [ ] Назва активної категорії унікальна без урахування регістру в межах одного користувача, включно з конкурентними запитами.
- [ ] Витрачена сума рахується лише за поточний календарний місяць у `APP_TIME_ZONE`.
- [ ] Залишок, відсоток, загальний бюджет і загальна використана сума відповідають формулам специфікації.
- [ ] Перевищення бюджету дозволене й помітне текстом та семантичним станом.
- [ ] Видалення архівує категорію, не видаляє витрати й не дозволяє використовувати категорію для нових витрат.
- [ ] Витрата посилається на `categoryId`; API не довіряє назві або обчисленим бюджетним полям із клієнта.
- [ ] Чужі категорії недоступні для читання та mutation; чужий UUID не розкриває існування ресурсу.
- [ ] Optimistic locking запобігає тихому перезапису новішої зміни.
- [ ] Shared Zod-схеми є джерелом істини для category DTO та API-відповідей.
- [ ] Структуровані логи містять `trace_id`, але не містять назв категорій або даних іншого користувача.
- [ ] Unit, API integration і web/E2E тести з розділу «Тести» проходять.
- [ ] `npm run build`, `npm run lint`, `npm run typecheck`, `npm run test` і `npm run format:check` проходять із кореня.
